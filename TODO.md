## Аутентификация

Сейчас панель полностью открыта: любой, кто имеет сетевой доступ к порту, видит
список внутренних сервисов с адресами. В локальной сети это приемлемо, при выносе
наружу — нет.

### Когда делать

Как только панель становится доступна за пределами доверенной сети: проброс порта
на роутере, публикация через домен, доступ из VPN-сегмента с чужими устройствами.
Пока панель слушает только LAN — задача не срочная.

### Варианты (от простого к сложному)

**1. Basic Auth на обратном прокси — предпочтительный вариант**

Аутентификация выносится из приложения в nginx/Caddy, код панели не меняется.

- nginx: `auth_basic` + `htpasswd`-файл;
- Caddy: директива `basic_auth` с bcrypt-хешем.

Плюсы: ноль кода, пароль не хранится в репозитории, там же терминируется TLS.
Минусы: один общий пароль на всех, нет выхода из сессии.

Обязательное условие: только поверх HTTPS, иначе пароль уходит открытым текстом.

**2. Basic Auth внутри приложения**

Если прокси нет и ставить его не хочется. Реализация — `before_request`-хук:
сверка логина и пароля из переменных окружения `PANEL_USER` / `PANEL_PASSWORD_HASH`
(хеш — `werkzeug.security.generate_password_hash`), сравнение через
`hmac.compare_digest`, ответ `401` с заголовком `WWW-Authenticate: Basic`.

- Пароль и хеш не коммитить: только окружение или `EnvironmentFile=` в юните.
- `/healthz` оставить без аутентификации, иначе сломается `ExecStartPost` в юните,
  либо проверять его отдельным токеном.
- Добавить проверки в `test_app.py`: 401 без заголовка, 200 с корректными
  учётными данными, 401 с неверным паролем.

**3. Внешний SSO (Authelia, authentik, oauth2-proxy)**

Оправдано, только если аутентификация нужна сразу нескольким домашним сервисам.
Для одной страницы со ссылками — избыточно.
